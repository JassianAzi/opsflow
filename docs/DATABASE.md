# OpsFlow Database Design

This document defines the initial logical database model.

Phase 1 defines the four authentication and organization tables in
`apps/api/src/db/schema.ts` with migration
`apps/api/drizzle/0000_soft_next_avengers.sql`. Phase 2 adds workflows and
workflow steps in `apps/api/drizzle/0001_previous_amazoness.sql`. Phase 3
Milestone 2 adds execution history and the durable queue outbox in
`apps/api/drizzle/0003_chilly_texas_twister.sql`. Milestone 4 adds dispatcher
lease ownership in `apps/api/drizzle/0004_mushy_mandarin.sql`. Tasks, audit,
and webhook tables below remain design targets.

The exact ORM syntax may change, but the domain model should remain consistent unless the architecture is intentionally revised and documented.

## 1. Tables

### users

Fields:
- id
- email
- password_hash
- display_name
- created_at
- updated_at

Constraints:
- UUID primary key generated by PostgreSQL
- a unique index on `lower(email)`; the API stores trimmed, lowercased email
- timestamps use `timestamptz` with database defaults

### sessions

Fields:
- id
- user_id
- token_hash
- expires_at
- created_at
- last_seen_at

Constraints and behavior:
- UUID primary key and foreign key to `users.id` with cascade delete
- unique index on `token_hash`, indexes on `user_id` and `expires_at`
- token hash is SHA-256 of a random 32-byte opaque token; raw token is never stored
- logout deletes the session; expired sessions are rejected during lookup

### organizations

Fields:
- id
- name
- slug
- created_by
- created_at
- updated_at

Constraints:
- UUID primary key, unique slug, foreign key from `created_by` to `users.id`
- slug includes a random suffix to allow duplicate organization names

### organization_members

Fields:
- id
- organization_id
- user_id
- role
- created_at

Roles:
- owner
- member

Constraints:
- unique organization_id + user_id
- UUID primary key; foreign keys to organization and user with cascade delete
- database enum `organization_role` allows `owner` and `member`
- index on `user_id` supports membership lookups
- creation of the organization and initial owner membership is transactional

### workflows

Fields:
- id
- organization_id
- name
- description
- status
- trigger_type
- trigger_config
- version
- created_by
- created_at
- updated_at

Statuses:
- draft
- active
- inactive

Constraints and behavior:
- UUID primary key, foreign keys to organization (`ON DELETE CASCADE`) and creator user
- PostgreSQL enums for status and trigger type (`manual`, `webhook`, `schedule`)
- `trigger_config` is JSONB and defaults to `{}`
- `version` starts at 1 and increments once per material definition change;
  status changes do not increment it
- check constraint requires `version >= 1`
- `created_at` and `updated_at` are `timestamptz`; the API updates the latter
- index on `(organization_id, updated_at)` supports scoped listing
- unique `(id, organization_id)` index supports a tenant-consistent composite
  execution foreign key
- workflow deletion is restricted after execution history exists; no execution
  row can be cascaded away by deleting a workflow

### workflow_steps

Fields:
- id
- workflow_id
- step_order
- step_type
- action_type
- name
- config
- retry_config
- created_at
- updated_at

Step types:
- condition
- action

Constraints and behavior:
- UUID primary key; workflow foreign key cascades on delete
- action type enum: `log`, `internal_task`, `mock_email`, `http_request`, `ai`;
  null for condition steps
- JSONB `config` and `retry_config` (`{}` default); no execution occurs yet
- unique `(workflow_id, step_order)` index; the API assigns consecutive
  zero-based positions from an ordered array and requires conditions before actions
- check constraints require nonnegative ordering and require action types only
  on action steps
- the Phase 2 PATCH API replaces step rows in one transaction when the step set
  changes; step IDs can change after an edit

### workflow_executions

Fields:
- id
- organization_id
- workflow_id
- workflow_version
- trigger_type
- trigger_payload
- workflow_snapshot
- idempotency_key
- status
- queued_at
- started_at
- completed_at
- error_message

Statuses:
- queued
- running
- completed
- failed
- cancelled

Constraints and behavior:
- UUID primary key; organization and workflow references use restrictive
  deletion
- composite `(workflow_id, organization_id)` foreign key prevents assigning an
  execution to a workflow from another tenant
- `workflow_version` is positive and identifies the captured definition
- `workflow_snapshot` is JSONB containing the immutable workflow metadata,
  trigger configuration, and ordered step snapshots
- `trigger_payload` and `workflow_snapshot` must be JSON objects
- optional idempotency keys are unique per workflow
- indexes support organization history, workflow history, and queued status
  scans
- started/completed timestamps cannot be reversed

### execution_steps

Fields:
- id
- execution_id
- workflow_step_id
- step_order
- step_type
- action_type
- name
- config
- retry_config
- status
- input_data
- output_data
- attempt_count
- started_at
- completed_at
- error_type
- error_message

Statuses:
- pending
- running
- completed
- skipped
- failed

Constraints and behavior:
- execution foreign key cascades only when an execution record is explicitly
  removed
- `workflow_step_id` is immutable provenance and intentionally has no foreign
  key to `workflow_steps`
- step type, action type, name, config, retry config, and order are copied from
  the execution snapshot so later workflow edits or step replacement cannot
  alter history
- unique `(execution_id, step_order)` ordering, nonnegative order and attempt
  count, condition/action consistency, JSON object checks, and timestamp order
  are enforced
- index on `(execution_id, status)` supports worker and detail queries

### execution_queue_outbox

Fields:
- id
- execution_id
- job_payload
- status
- attempt_count
- available_at
- locked_at
- lock_token
- published_at
- last_error
- created_at
- updated_at

Statuses:
- pending
- published
- failed

Constraints and behavior:
- one outbox row per execution
- execution foreign key cascades only when an execution is explicitly removed
- `job_payload` must equal `{ "executionId": execution_id }`; workflow
  definitions and trigger data stay in PostgreSQL
- attempt count is nonnegative and `(status, available_at)` is indexed for the
  dispatcher
- the dispatcher claims available rows with `FOR UPDATE SKIP LOCKED`, records a
  UUID `lock_token`, and accepts completion or failure updates only from that
  claim owner
- publication failures retain a redacted `last_error` and advance
  `available_at`; bounded attempts end in `failed`
- `published_at` is set only after BullMQ acknowledges the deterministic
  execution-ID job

### internal_tasks

Fields:
- id
- organization_id
- execution_id
- title
- description
- status
- created_at
- completed_at

Statuses:
- open
- completed

### audit_logs

Fields:
- id
- organization_id
- user_id
- action
- entity_type
- entity_id
- metadata
- created_at

### webhook_endpoints

Fields:
- id
- organization_id
- workflow_id
- public_id
- secret_hash
- enabled
- created_at
- updated_at

## 2. JSON Columns

PostgreSQL JSONB may be used for:
- trigger_config
- workflow step config
- retry_config
- trigger_payload
- step input_data
- step output_data
- audit metadata

JSON must not replace fields that need frequent indexing or relational integrity.

## 3. Tenant Isolation

Every tenant-owned resource must be traceable to an organization.

API queries must never retrieve organization-owned data without organization scoping.

Unsafe:

```sql
SELECT * FROM workflows WHERE id = $1;
```

Preferred:

```sql
SELECT * FROM workflows
WHERE id = $1
AND organization_id = $2;
```

## 4. Migrations

Rules:
- all schema changes require migrations
- never manually modify production-like schema without a migration
- migration files are committed
- destructive migrations must be explicitly documented

Run `npm run db:migrate` against the intended `DATABASE_URL`. Phase 1 and
Phase 2 generated migrations with `npm run db:generate` and applied them to a dedicated
`opsflow_test` database. No seed data exists yet. API integration tests apply
committed migrations to a dedicated database named `opsflow_test` and clear
only their own fixture rows between tests.

Phase 2 remediation adds `apps/api/drizzle/0002_sticky_joseph.sql`. Before it
was applied locally, explicit queries found zero invalid versions, negative
orders, or inconsistent step/action types in `opsflow_test`.

Phase 3 Milestone 2 adds
`apps/api/drizzle/0003_chilly_texas_twister.sql` without modifying migrations
0000–0002. It was applied from scratch to a disposable PostgreSQL 16
`opsflow_test` database before database-backed tests ran; the disposable
container was then removed.

## 5. Seed Data

Development seed data should include:
- one demo user
- one demo organization
- one sample workflow
- several execution histories with different statuses

Do not commit real credentials.
